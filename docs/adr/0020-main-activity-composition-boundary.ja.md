# ADR-0020: MainActivityをAndroidの構成境界に保つ

状態: 採用

## 決定事項

`MainActivity`の責務をAndroidライフサイクルとの接続とオブジェクト構成に限定していく。
常に有効な状態遷移と機能横断の判断はプラットフォーム非依存のmodelまたはviewer型へ、
永続化はrepository portの背後へ、繰り返されるAndroid View生成は専用のpresentation部品へ移す。

コードは呼び出し順ではなく抽象度で配置する。機能横断モデルは`model`、閲覧の振る舞いは
`viewer`、保存対象の概念は`file`、アダプタは`infrastructure`、Android表示と
ライフサイクル配線は`presentation`に置く。`MainActivity`は各部品を調停できるが、
各部品が所有する規則を再実装してはならない。

## 検討した選択肢

- Androidコールバックの起点であることを理由に画面の振る舞いをすべて`MainActivity`へ残す。
- Activityをライフサイクルの段階ごとのhelperにだけ分割する。
- 大規模なpresentation frameworkを導入して画面を書き直す。
- 所有権と抽象度に従って振る舞いを段階的に抽出する。

## 選択理由

Activityには描画、永続化、タブ復元、ピン留め、View生成の規則が蓄積していた。
規則がViewだけに存在すると、別の操作経路がその処理を忘れて機能退行を起こし得る。
プラットフォーム非依存の所有者は規則を直接テスト可能にし、専用Android rendererは
ドメイン判断をUI helperへ隠さずView生成の雑音を減らす。段階的な抽出なら、公開済みの
アプリを各段階で検証可能な状態に保てる。

## 選択しなかった理由

Activity中心の設計は時間的結合とAndroid依存テストを残す。ライフサイクル別の分類は、
意味ではなく実行時期でコードを分類してしまう。frameworkを使った全面改修は、
ドメインモデルの改善に比例しない大きなリリースリスクを生む。

## 決定を見直す契機

Androidライフサイクル配線が十分小さく安定して別の構成ルートが適切になったとき、
複数画面で同じpresentation状態所有者が必要になったとき、または計測により現在の
抽象境界が削減する以上の変換コストを生んでいると分かったときに見直す。
